# Правила работы с Git

## Основная ветка и рабочие ветки

Основная ветка проекта — `main`. Создавайте отдельную ветку от актуальной `main` для каждой задачи и направляйте pull request в `main`.

Используйте короткие имена веток на английском языке, например `feat/disk-history`, `fix/agent-timeout` или `docs/git-workflow`.

```sh
git switch main
git pull --ff-only
git switch -c docs/git-workflow
```

Не переписывайте опубликованную историю `main` и не выполняйте force push в неё. Согласовывайте переписывание истории общей рабочей ветки с её участниками.

## Формат коммитов

Мы используем Conventional Commits. Все сообщения коммитов, включая заголовок, описание и служебные примечания, пишутся на английском языке.

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

Выбирайте тип по назначению изменения:

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `docs` — документация.
- `refactor` — изменение структуры кода без изменения поведения.
- `test` — добавление или изменение тестов.
- `style` — форматирование кода без изменения поведения.
- `perf` — улучшение производительности.
- `build` — сборка или зависимости.
- `ci` — настройки автоматических проверок и публикации.
- `chore` — прочие задачи обслуживания.

Scope необязателен; используйте название затронутой части, например `agent`, `server` или `frontend`. Описание делайте коротким, в повелительном наклонении, без точки в конце. В теле коммита при необходимости объясняйте причину изменения и существенные последствия.

```text
feat(agent): add disk temperature history
fix(server): handle agent connection timeouts
docs: document Git workflow
```

Несовместимое изменение обозначайте `!` перед двоеточием или примечанием `BREAKING CHANGE:` с объяснением необходимых действий:

```text
feat(agent)!: rename the history retention setting

BREAKING CHANGE: Replace history.days with history.retention_days in YAML configuration.
```

## Подготовка изменений и pull request

Один коммит должен содержать одно логически связанное изменение. Перед коммитом просмотрите `git diff` и добавляйте в индекс только относящиеся к задаче файлы. Проверьте итоговый состав через `git diff --cached`.

Запустите подходящие проверки из [инструкции разработки](development.md). Не включайте токены, приватные ключи, базы SQLite, сгенерированные файлы и сведения о домашней инфраструктуре.

В pull request опишите проблему, итоговое поведение, выполненные проверки и существенные ограничения. Добавьте ссылки на связанные задачи и обезличенные снимки интерфейса, если они помогают проверке. При squash-слиянии итоговое сообщение коммита также должно соответствовать Conventional Commits и быть на английском языке.
